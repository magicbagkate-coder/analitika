## Что это за проект

Бэкенд-сервис на NestJS + TypeScript, который интегрируется с CRM Sitniks
(`https://crm.sitniks.com/open-api`) для магазина MagicBag (сеть также
включает «Краса і Уход»).

Задача: читать переписки менеджеров с клиентами в Sitniks, оценивать
каждый диалог по шкале 1–5 (тег `оценка-N`, где 1 = очень плохо, 5 = супер),
писать заметку (note) — короткий структурированный разбор: что менеджер
сделал хорошо, почему клиента не закрыли (или что сработало, если закрыли),
конкретные ошибки менеджера, обязательно с ником/именем клиента, и в конце
дня формировать сводку по каждому менеджеру. Формат заметки намеренно
короткий и прикладной — владелица должна прочитать каждую за ~10 секунд,
без эссе; полный формат промпта — в `claude/claude.service.ts`.

Общие правила стиля кода и работы — в `CLAUDE.md` уровнем выше (в папке
«Клод» на рабочем столе). Этот файл — про сам проект, а не про стиль кода.

## Архитектурные решения (заданы владелицей проекта явно, не менять без её слова)

- С 2026-09-14 — Docker (Dockerfile + docker-compose.yml) и Postgres
  (TypeORM, `src/database/database.module.ts`) на сервере; см. раздел
  «Как это всё запущено сейчас» ниже. Postgres пока без entity под
  бизнес-данные — провизия на будущее, не выдумывать схему без реальной
  задачи. Данные по-прежнему в основном идут напрямую в Sitniks (теги,
  заметки), либо в память процесса (дневная статистика), либо в локальные
  файлы (`reports/*`) — БД это не заменяет, пока нет конкретной причины.
- Весь код — TypeScript.
- Проект — монолит, таким и останется (явное решение контрактора
  владелицы 2026-09-14, не дробить на сервисы). Один модуль NestJS на
  один эндпоинт/узел интеграции Sitniks внутри монолита (принцип единой
  ответственности: список чатов, сообщения чата, заметки чата, обновление
  чата, менеджеры — отдельные модули); общую логику — в shared-файлы
  (`telegram-format.ts`, `manager-context.ts`), не дублировать. Не
  сливать модули друг с другом ради удобства.
- Тестов пока нет — будут позже, по отдельному запросу.
- У Sitniks нет вебхуков — сервис работает поллингом (см.
  `sitniks-chat-poller`).
- Отчёты (ежедневная сводка и снимок статуса) пишутся в локальный файл
  (`reports/*.txt`) И отправляются в Telegram-бота `@MagicBag_analis_bot`
  (`TelegramService`, токен/chat_id — в `.env`). Файл — просто бэкап,
  основной канал для владелицы — Telegram.
- Уже потрачены реальные деньги на Claude API — экономия токенов важна:
  чат с тегом `оценка-*` пропускается, ПОКА в нём не появилось новых
  сообщений с последней оценки (тег `msg-<id>` хранит id последнего
  учтённого сообщения; см. `needsEvaluation` в
  `evaluation/evaluation.constants.ts`) — «Вибір товару» живёт днями с
  касаниями каждый час, поэтому разовая оценка навсегда не подходит.
  Статичная часть промпта кэшируется (`cache_control: ephemeral` в
  `claude.service.ts`).

## Структура модулей (src/)

- `config/` — `AppConfigService`, чтение `.env`.
- `sitniks-client/` — общий HTTP-клиент к Sitniks (авторизация Bearer,
  GET/POST/PUT).
- `sitniks-chat-list/` — список чатов.
- `sitniks-chat-messages/` — сообщения внутри чата.
- `sitniks-chat-notes/` — создание заметок к чату.
- `sitniks-chat-update/` — обновление чата (простановка тега).
- `sitniks-chat/` — базовый модуль по чату (get one).
- `sitniks-managers/` — список менеджеров.
- `evaluation/` — вызывает Claude (`claude/` модуль) для оценки диалога,
  публикует тег (`оценка-N` + служебный `msg-<id>`) + заметку (только
  блок «Рекомендация к закрытию», без HTML) обратно в Sitniks.
  `TARGET_STATUS` и `needsEvaluation` (нужна ли переоценка) — здесь же,
  в `evaluation.constants.ts`, общие для status-report и (отключённого)
  поллера.
- `sitniks-chat-poller/` — раз в 5 минут ищет затихшие чаты. **Код рабочий,
  но модуль НЕ подключён в `app.module.ts`** (см. «Как это всё запущено
  сейчас» — конфликтует по стоимости с status-report для «Вибір товару»).
- `daily-stats-store/` — накопитель оценок в памяти за день (без БД);
  сейчас никто в него не пишет, т.к. поллер отключён.
- `daily-summary/` — раз в сутки (в 23:00) пишет сводку в файл и в
  Telegram, очищает накопитель. **Модуль НЕ подключён в `app.module.ts`**
  (избыточен поверх status-report, см. ниже).
- `status-report/` — дважды в сутки (15:45 и 23:45 точно до минуты, см.
  `status-report.constants.ts` — `REPORT_TIMES`; `TARGET_STATUS` живёт в
  `evaluation/evaluation.constants.ts`) снимает срез всех чатов в статусе,
  оценивает новые/изменившиеся с последней оценки (`needsEvaluation`),
  шлёт в Telegram отдельным сообщением на каждый чат (эмодзи + жирные
  подписи блоков — формат в `status-report-formatter.ts`, см. память
  проекта про Telegram-формат) плюс ИТОГ-сводку с распределением оценок,
  плюс — ОТДЕЛЬНЫМ сообщением после ИТОГ, не внутри него — блок «На что
  обратить внимание» (`formatAttentionBlock`, пусто → ничего не шлём), и
  пишет то же в файл.
- `bulk-tag-status/` — разовая административная задача (уже выполнена,
  проставила тег «1» чатам в статусе «ТЕСТ КАТЯ»); можно удалить модуль.
- `telegram/` — `TelegramService.sendMessage` в Bot API, токен/chat_id
  из `.env` (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`). Бот —
  `@MagicBag_analis_bot`. `telegram-format.ts` — общие `escapeHtml`/
  `formatManagerNames`, используются и `status-report-formatter.ts`, и
  `order-success-analysis-formatter.ts`.
- `order-success-analysis/` — добавлен 2026-09-14. Дважды в сутки, на том
  же расписании (`REPORT_TIMES` из `status-report.constants.ts`), смотрит
  статус «Замовлення створено» (`ORDER_CREATED_STATUS`) — сделки, которые
  УЖЕ закрыты. Вопрос другой, чем у `status-report`: не «насколько хорошо
  отработал менеджер», а «что конкретно привело к продаже»
  (`ClaudeSuccessService.analyzeSuccessFactors`, отдельный от
  `claude.service.ts` промпт). Оценка здесь детерминирована, не отдана на
  усмотрение Claude: 5, если была реально подтверждённая допродажа
  (`hadUpsell`), иначе 4 (`SCORE_WITH_UPSELL`/`SCORE_WITHOUT_UPSELL` в
  `order-success-analysis.service.ts`) — владелица явно это попросила
  («если есть допродажа — 5, если нет — 4»). Тег переиспользует тот же
  `оценка-N` (общий `SCORE_TAG_PREFIX`), что и «Вибір товару», и ЗАМЕНЯЕТ
  прежнюю оценку чата, если она там была — раз сделка закрыта, финальная
  оценка важнее промежуточной. Собственный трекинг переоценки — отдельный
  тег (`успіх-аналіз-v2` + `succ-msg-<id>`, см.
  `order-success-analysis.constants.ts`) и своя переоценка при новых
  сообщениях (`needsSuccessAnalysis`, та же логика, что `needsEvaluation`
  в `evaluation/`, но отдельно — не может опираться на наличие `оценка-`,
  так как чат из «Вибір товару» уже может её нести, не будучи ещё
  разобран этим модулем). **Заметку в Sitniks НЕ пишет** (явное решение
  владелицы 2026-09-14 — заметки только в «Вибір товару»), только тег и
  блоки в ту же Telegram-группу, плюс отдельным сообщением (как и у
  status-report) «Що системно веде до угод» —
  `ClaudeSuccessService.synthesizeSuccessPatterns` +
  `formatSuccessAttentionBlock`.
- `evaluation-history/` — добавлен 2026-09-14. Не орган расписания, просто
  Postgres-хранилище (`EvaluationHistoryEntity`/`evaluation_history`,
  миграция `database/migrations/`): и `EvaluationService`
  («Вибір товару»), и `OrderSuccessAnalysisService` («Замовлення
  створено») пишут туда через `EvaluationHistoryService.tryRecord` после
  каждой публикации оценки — `source: 'product_selection' |
  'order_created'`, `note` = mistakes или successFactors соответственно.
  Единственный читатель пока — `manager-trends/`.
- `manager-trends/` — добавлен 2026-09-14 по явной просьбе владелицы:
  «История и тренды по менеджерам». Раз в неделю (`WEEKLY_DIGEST_TIME` в
  `manager-trends.constants.ts`, по умолчанию понедельник 10:00 по
  Києву) читает `evaluation_history` за последние
  `TREND_LOOKBACK_WEEKS` (сейчас 5) скользящих 7-дневных периодов,
  **только `source: 'product_selection'`** (оценки «Замовлення створено»
  — другая шкала, деструктивно исказили бы тренд качества, специально
  исключены). Два независимых сигнала: (1) детерминированный тренд
  оценки вверх/вниз `MIN_WEEKS_FOR_TREND` (3) недели подряд подряд, без
  участия Claude — считается в коде; (2) одна и та же повторяющаяся
  ошибка у менеджера несколько недель подряд —
  `ClaudeTrendsService.synthesizeRecurringIssues`, отдельный Claude-вызов.
  Если ни того, ни другого нет — сообщение не отправляется вообще.

## Миграции базы данных

`synchronize: false` в `DatabaseModule` намеренно (см. `.claude`-историю
проекта) — схема только через миграции TypeORM, не автосинк. Новая
миграция — файл в `src/database/migrations/`, руками (`up`/`down` SQL,
без генератора, так как локальная машина не имеет сетевого доступа к
Postgres на сервере — сервис `postgres` виден только изнутри
docker-сети). Прогон миграций — **на сервере**, после `git pull` и
`docker compose up -d --build`:
```
sudo docker compose -f /home/cloud/analitick/docker-compose.yml exec app npm run migration:run:prod
```
(`migration:run` — локальный/dev-вариант через ts-node, `migration:run:prod`
— через собранный `dist/database/data-source.js`, именно он актуален на
сервере).

## Как это всё запущено сейчас (важно!)

**С 2026-09-14 автоматизация работает на сервере, не на локальной машине.**
Локальный `npm run start:dev` / `node dist/main.js` на Windows-машине
владелицы ОСТАНОВЛЕН намеренно и НЕ должен запускаться снова — если
нужно проверить статус, смотреть контейнер на сервере, не гадать и не
поднимать локальный процесс «на всякий случай» (иначе задвоятся отчёты).

**Сервер**: VPS `116.204.153.123`, пользователь `cloud`, passwordless
sudo, Ubuntu, таймзона UTC. Код в `/home/cloud/analitick`, поднят через
`docker compose` (см. `docker-compose.yml` в корне — сервисы `app` +
`postgres:16.4-alpine`, именованный volume `magicbag_postgres_data`
переживает `docker compose down` без `-v`).

**Деплой — только `git`, без CI/CD** (так решил технический контрактор
владелицы 2026-09-14): правки локально → `git push` в
`https://github.com/magicbagkate-coder/analitika` → на сервере `cd
/home/cloud/analitick && git pull && sudo docker compose up -d --build`.
Локальная машина — только для написания кода, сборка/прогон — на
сервере.

**Расписание — строго киевское время, независимо от таймзоны хоста**
(`getKyivHourMinute()` в `status-report.constants.ts`, `Intl.DateTimeFormat`
с `timeZone: 'Europe/Kyiv'`) — сервер работает в UTC, локальная машина
была в Kyiv-time, отсюда реальный баг при переезде: расписание раньше
читало голое `Date#getHours()`, что на UTC-сервере стреляло бы на 3 часа
не в то время. Если снова трогаешь `checkAndRun`/`formatReportTime` в
`status-report.service.ts` или `order-success-analysis.service.ts` —
только через `getKyivHourMinute()`, никогда через голый `new Date()`.

Работает `StatusReportModule` (дважды в день, 15:45 и 23:45 по Киеву, по
статусу «Вибір товару») И `OrderSuccessAnalysisModule` (то же расписание,
статус «Замовлення створено», см. раздел про модули выше) —
`SitniksChatPollerModule` и `DailySummaryModule` сознательно НЕ
подключены в `app.module.ts`, см. комментарий там.

`.env` на сервере создан вручную (боевые `SITNIKS_API_KEY`,
`ANTHROPIC_API_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` перенесены
с локальной машины; `POSTGRES_PASSWORD` сгенерирован случайно), загружен
по SFTP (не через SSH-команду — риск проблем с экранированием спецсимволов
в секретах), права `600`. Локальный `.env` (для разработки/точечных
проверок API) создан через `setup-env.bat`.

## Известные ограничения Sitniks API (на момент последней сессии)

- `POST /open-api/chats/{chatId}/notes` — раньше стабильно отвечал `403
  forbidden_resource`, Sitniks признали баг и 2026-09-10 подтвердили
  исправление; перепроверено напрямую (`201 Created`) на тестовом чате.
  Заметки снова создаются нормально. `evaluation.service.ts` всё равно
  оставлен со «мягким» `tryCreateNote` (не роняет процесс оценки, только
  логирует warning) — на случай регресса, а не потому что баг ещё жив.
- Реальная форма ответов Sitniks в паре мест разошлась с их же
  OpenAPI-схемой на момент проверки: у чата поле id называется `id`, а
  не `_id`, как в схеме; `assignedManagerId` может либо отсутствовать,
  либо быть явно `null` (не только `number`) — оба случая обработаны в
  типах. Если форма ответа снова поменяется — своих диагностических
  сбросов в код больше не встраивать, просто дёрнуть `/open-api/chats`
  напрямую и свериться.

## Как я работаю с этим проектом

Владелица не хочет печатать/выполнять команды в терминале — сама этого
не делает, ждёт, что команды (включая запуск/остановку `npm run
start:dev`) выполняю я. Не переспрашивать повторно про доступ к
терминалу. Работать нужно через:
- прямые правки файлов на её компьютере, которые подхватывает `--watch`
  (процесс сейчас запущен — см. раздел про автоматизацию выше);
- сам запускаю/останавливаю `npm run start:dev` в фоне по её команде
  («запускай автоматизацию» / «останови автоматизацию»);
- ручной разбор конкретных чатов/статусов — не обязательно через сервис,
  можно и нужно напрямую запросами к Sitniks API (Bearer-токен из
  `.env`), это быстрее для одноразовых запросов;
- запись диагностики в файлы (`reports/*.json`, `reports/*.txt`), если
  нужно что-то передать между сессиями;
- просьбу вставить текст из терминала — только как самая последняя мера.

Docker и npm install — не просить её выполнять без крайней необходимости
(один раз уже был случай, что добавленный, но не установленный пакет
`@nestjs/schedule` уронил процесс — с тех пор планировщик сделан на
обычном `setInterval`, без сторонних пакетов).

**Разовые скрипты (`scripts/`, например `recalibrate.ts`) — только через
`ts-node -P scripts/tsconfig.json`, никогда как обычный файл в `src/`.**
`scripts/` явно исключена из `tsconfig.json` И `tsconfig.build.json`
(у `tsconfig.build.json` свой `exclude`, не наследуется от родителя через
`extends` — если добавляешь исключение, править оба файла). 2026-09-11 файл
вне `src/` без этого исключения сломал `tsc`'s `rootDir`, `nest start
--watch` молча перестал пересобираться при каждой правке кода, а
сама автоматизация не присылала отчёты 3 дня (с вечера пятницы по
воскресенье) — заметили только когда владелица сказала, что ничего не
пришло. После любого файла вне `src/` — сразу `npm run build` и проверка
вывода живого dev-сервера (не только `tsc --noEmit`, у него свой конфиг).
